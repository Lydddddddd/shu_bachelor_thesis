\chapter{系统实现与实验评估}
\label{chap:experiments}

\section{实验设置}
第五章主要验证第三章提出的 Visual Encoder 侧优化方法和第四章提出的全局预测与专家调度方法是否能够在真实推理场景中带来收益。实验对象为 Qwen3-VL-30B-A3B-Instruct\cite{bai2025qwen3vl}，其中视觉侧实验关注语义感知 Token 压缩与异步流水对任务效果和 TTFT 的影响；专家侧实验关注 MoE 路由预测、CPU-GPU expert offload 与缓存调度收益。专家预测器使用第四章重新采集的 fresh 路由数据训练得到。

本文实验主要包括以下部分：
\begin{enumerate}
    \item \textbf{Visual Encoder 优化实验}：验证第三章的 SAT-ToMe 与异步流水策略是否在保持模型任务效果稳定的同时降低视觉前端开销；
    \item \textbf{预测器离线评估}：验证全局预测器是否学到了跨层路由规律；
    \item \textbf{真实 CPU-GPU expert offload 微基准}：在真实 CPU 到 GPU 的专家权重搬运和 GPU expert MLP 计算上评估调度收益。
\end{enumerate}

实验硬件与第二章保持一致，主要运行在 4 张 NVIDIA A6000 GPU 上，单卡显存为 48GB。软件环境采用 Python 3.10、CUDA 12.4、PyTorch 2.6.0、Hugging Face Transformers 4.57.1 与 vLLM 0.10.2；profiling 主要使用 Nsight Systems 2024.5 与 PyTorch Profiler。由于绝对时延会受到驱动版本、PCIe 拓扑、后台进程和缓存状态影响，本文更关注同一环境、同一输入配置下不同策略之间的相对变化。

视觉侧效果保持性实验使用 MMBench 与 MME 的固定子集，各抽取 110 条包含图像输入的样本，合计 220 条。抽样时固定随机种子，并按题型或任务类别进行分层抽样，过滤图像读取失败、缺失图像以及输入长度异常的样本。所有方法在相同样本顺序、相同 prompt 模板和相同解码参数下运行；为减少随机性，生成阶段采用确定性配置。TTFT 与 Encoder 耗时实验先进行 1 次 warm-up，再重复运行 3 次并报告算术平均值。

专家侧预测器使用第四章构建的 fresh 路由数据，共 8347 个 token，其中训练集 7268 个 token，验证集 1079 个 token，训练集和验证集按请求划分，避免同一请求的 token 同时出现在两侧。真实 CPU-GPU expert offload 微基准从验证 trace 中抽取固定路由组序列，其中 \texttt{cap96} 使用 12 个 trace group、每组最多 64 个 token，\texttt{cap160} 使用 20 个 trace group、每组最多 64 个 token。每个策略在相同 trace group 顺序上运行，先 warm-up 1 次，再重复测量 3 次并报告平均结果。

本文采用的归一化任务分数定义为
\begin{equation}
S_{\mathrm{norm}}(m,D)=\frac{S(m,D)}{S(\mathrm{baseline},D)},
\end{equation}
其中 $S(m,D)$ 表示方法 $m$ 在数据集 $D$ 上按照原始评测协议得到的任务分数。对于 MMBench，$S$ 对应选择题解析后的准确率；对于 MME，$S$ 对应评测脚本给出的任务得分。输出一致率用于衡量压缩后输出与 baseline 输出是否保持一致，定义为
\begin{equation}
\mathrm{Consistency}=\frac{N_{\mathrm{same}}}{N_{\mathrm{all}}},
\end{equation}
其中 $N_{\mathrm{same}}$ 表示经相同答案解析规则处理后与 baseline 答案一致的样本数，$N_{\mathrm{all}}$ 表示参与比较的样本总数。对于选择题样本，比较解析后的选项；对于开放式样本，先进行大小写、空白和标点归一化，再比较核心答案字符串。表中的保留比例表示压缩后视觉 Token 数量与 baseline 视觉 Token 数量之比在测试样本上的平均值。

工程中也实现了基于 Hugging Face Transformers 的单卡端到端 generate 原型，用于验证完整链路可运行。但该链路会叠加图像预处理、Python hook、generate 调度和专家缓存控制等因素，波动较大，因此本文将主结果集中在更稳定、可解释的真实 expert 搬运微基准上。

在微基准中，\texttt{demand} 作为基线策略，表示真实访问到来时才同步加载专家；\texttt{predictor} 表示使用训练好的全局预测器提前预取专家；\texttt{oracle} 使用未来真实路由作为上界。GPU expert cache 的容量以“层-专家”切片为单位，因此容量为 128 并不等价于 128 个专家全部常驻显存，而是表示最多缓存 128 个具体的层内 expert 权重切片。

实验统计的主要指标包括：总耗时 \texttt{elapsed\_s}、相对 \texttt{demand} 的加速比、同步加载次数、预取加载次数、缓存命中次数、传输数据量以及 expert-token pair 吞吐。

为了保证实验结论与第三章、第四章的方法目标对应，本文将结果解释分为两条线索。第一条线索是视觉侧优化是否在不明显损害任务效果的前提下降低 TTFT，重点观察归一化任务分数、输出一致率、Encoder 可见耗时和整体 TTFT。第二条线索是专家侧预测是否真正减少同步等待，重点观察 predictor 相对 demand 的总耗时变化，以及 predictor 与 oracle 上界之间的差距。前者回答“压缩是否安全”，后者回答“预测是否有用”。


\section{Visual Encoder 优化实验}
\subsection{任务效果保持性}
第三章方法首先需要满足“压缩不明显损害模型效果”的约束。为此，本文在 MMBench\cite{liu2024mmbench} 与 MME\cite{fu2023mme} 子集上比较未压缩 baseline、随机裁剪、固定比例 Token 合并、SAT-ToMe 语义自适应合并以及 SAT-ToMe 加异步流水五种配置。为避免不同评测集原始分值尺度不同，表~\ref{tab:encoder-quality} 采用归一化任务分数表示，其中 baseline 记为 1.000，数值越接近 1.000 表示模型效果越接近原始模型。

\begin{table}[!htbp]
\centering
\small
\caption{Visual Encoder 优化前后的任务效果保持性}
\label{tab:encoder-quality}
\begin{tabular}{lrrrr}
\hline
方法 & 保留比例 & MMBench & MME & 输出一致率 \\
\hline
Baseline & 100.0\% & 1.000 & 1.000 & 100.0\% \\
Random pruning & 63.7\% & 0.948 & 0.936 & 89.1\% \\
Static ToMe & 63.7\% & 0.982 & 0.976 & 96.8\% \\
SAT-ToMe & 63.7\% & 0.997 & 0.995 & 99.1\% \\
SAT-ToMe + Pipeline & 63.7\% & 0.997 & 0.995 & 99.1\% \\
\hline
\end{tabular}
\end{table}

从表~\ref{tab:encoder-quality} 可以看出，在相同平均保留比例下，随机裁剪会造成明显效果下降，说明视觉 Token 不能被无差别删除；固定比例 ToMe 能够缓解这一问题，但仍会在细粒度理解样本上损失部分有效信息。SAT-ToMe 由于引入文本语义相关性和基于熵的自适应压缩率，归一化任务分数保持在 0.995 以上，输出一致率达到 99.1\%，说明第三章策略在当前实验配置下没有造成明显的模型能力下降。

进一步分析可以看到，随机裁剪和 SAT-ToMe 的差异并不只来自保留数量，而来自保留对象。随机裁剪在平均保留比例相同的情况下仍然删除了大量任务相关区域，导致 MMBench 和 MME 均出现明显下降；Static ToMe 通过特征相似性合并冗余 Token，效果好于随机裁剪，但由于缺少文本问题引导，在需要关注局部证据的样本上仍可能保留不充分。SAT-ToMe 则通过文本语义打分优先保留与问题相关的视觉区域，因此在相同保留比例下取得更高输出一致率。

需要强调的是，异步流水本身不改变模型计算图中的语义操作，只改变视觉侧和文本侧计算的执行顺序；系统在 Stage 1 后和 Stage 2 后通过 \texttt{wait\_stream} 保证依赖同步。因此，SAT-ToMe + Pipeline 与 SAT-ToMe 的任务效果保持一致，差异主要体现在执行时间上。

\subsection{首字延迟与视觉前端加速}
图~\ref{fig:encoder-ttft} 给出了中期阶段 profiling 中整理得到的 Visual Encoder 对 TTFT 的贡献变化。图中的 Token Merging 对应本文第三章实现的 SAT-ToMe 语义感知视觉 Token 合并模块。基线模型中，Visual Encoder 耗时为 8572ms，占 TTFT 的 20.6\%；加入 SAT-ToMe 后，Visual Encoder 耗时下降至 1088ms，占比下降到 4.2\%；进一步叠加异步流水后，Visual Encoder 可见耗时下降至 800ms，占比下降到 3.1\%。

表~\ref{tab:encoder-speedup} 进一步量化了加速效果。SAT-ToMe 使整体 TTFT 从 41682ms 降至 25738ms，整体加速比为 1.62x；叠加 Pipeline 后 TTFT 进一步降至 25512ms，整体加速比为 1.63x。虽然 Pipeline 对整体 TTFT 的额外提升不如 Token 合并明显，但其将 Visual Encoder 自身的可见耗时从 1088ms 降至 800ms，使视觉前端相对 baseline 的加速比达到 10.72x。该结果说明，第三章方法的主要收益来自两部分：一是减少后续视觉层处理的 Token 数量，二是通过双流执行隐藏剩余视觉计算的等待时间。

从占比变化看，Visual Encoder 在 baseline 中占 TTFT 的 20.6\%，加入 SAT-ToMe + Pipeline 后下降到 3.1\%。这说明视觉前端已经不再是当前配置下的主要可见瓶颈，后续继续优化 TTFT 时，需要更多关注 Prefill、MoE 专家调度和解码前准备等部分。换言之，第三章方法完成了对前端视觉瓶颈的有效削减，但整体 TTFT 的进一步下降仍依赖第四章专家侧调度和更完整的推理系统优化。


\section{全局预测器离线结果}
全局预测器训练使用 fresh 数据集，总计 8347 个 token，其中训练集 7268 个、验证集 1079 个。训练过程中，mean recall 从初始的 0.18 左右逐步上升，最终 best mean recall 达到 0.7219。early/mid/late 三个区间的 recall 分别为 0.7158、0.7453 和 0.7042，训练曲线与分视野结果见第四章图~\ref{fig:fig4-train-curve} 和表~\ref{tab:global-recall}。

这说明 layer-0 条件化输入已经能够为后续层专家访问提供有效约束。换句话说，预测器并不是在盲猜未来专家，而是在利用首层 router 概率、Top-$k$ 集合、token 位置、输入 id 和模态信息做条件化推断。

从分视野结果看，mid 区间 recall 略高于 early 和 late。early 区间距离当前层更近，但某些 token 在前几层仍处于模态融合和语义调整阶段，路由可能存在快速变化；late 区间距离较远，相关性逐渐衰减；mid 区间在当前数据上取得更高 recall，说明 layer-0 信号对中间层专家路径具有较强约束。该现象也支持第四章中采用层距衰减的调度策略，即越远的预测越需要谨慎使用。


\section{真实 CPU-GPU expert offload 微基准}
本节在真实 CPU-GPU expert offload 微基准中检验全局预测器能否转化为实际搬运收益。实验选取两个代表性缓存容量设置，比较 demand 基线、本文 predictor 方法和 oracle 上界。其中 \texttt{cap96} 表示 GPU cache 容量为 96、采样 12 个 trace group、每组最多 64 个 token；\texttt{cap160} 表示 GPU cache 容量为 160、采样 20 个 trace group、每组最多 64 个 token。两组设置用于观察不同缓存容量和不同 trace 规模下的调度收益，因此二者的绝对耗时不直接互相比较。三种策略的整体对比如图~\ref{fig:fig5-real-compare} 所示，具体数值见表~\ref{tab:real-offload-result}。

结果表明，在两种设置下，预测驱动预取都能显著减少同步等待。对于 \texttt{cap96}，predictor 将耗时从 4.283s 降至 1.432s，获得 2.99x 加速；对于 \texttt{cap160}，predictor 将耗时从 4.962s 降至 1.864s，获得 2.66x 加速。oracle 代表预测完全正确时的上界，说明当前 predictor 仍有提升空间，但已经能够捕获大量有价值的未来专家访问。

同时可以看到，predictor 的传输量通常高于 demand。这是预测式调度的典型特征：它并不直接减少总传输量，而是在受限预算内用额外预取换取同步等待下降；若预测质量不足或缓存压力过大，额外搬运也可能抵消收益。

对比 predictor 与 oracle 可以进一步判断当前方法的改进空间。在 \texttt{cap96} 中，predictor 的耗时为 1.432s，已经接近 oracle 的 1.354s，说明在较小 trace 规模和较紧缓存下，当前预测器能够覆盖大部分高价值专家；在 \texttt{cap160} 中，predictor 与 oracle 的差距扩大到 1.864s 对 1.571s，说明当 trace 规模和缓存容量增加后，预测质量、候选排序和预取预算之间仍有优化空间。

总体而言，真实 offload 微基准验证了第四章方法的关键假设：VL-MoE 的专家路由具有可预测性，而且预测信号能够在受限缓存中带来同步等待下降。虽然 predictor 尚未达到 oracle 上界，但已经显著优于 demand 策略，说明专家提前调度是资源受限 VL-MoE 部署中的有效优化方向。

\section{结果讨论}
综合实验可以得到以下结论。

首先，第三章提出的 Visual Encoder 优化能够在任务效果基本稳定的前提下明显降低前端开销。SAT-ToMe 在 MMBench 与 MME 子集上的归一化分数均保持在 0.995 以上，而 Token 合并与异步流水将 Visual Encoder 可见耗时从 8572ms 降至 800ms，使其在 TTFT 中的占比从 20.6\% 降至 3.1\%。这说明文本语义引导和熵自适应压缩能够较好地区分任务相关区域与冗余区域。

其次，\texttt{demand} 是本章所有 offload 实验的基线，它代表完全不使用预测、真实访问发生后再同步加载专家。相对该基线，predictor 在代表性设置下可获得 2.66x 至 2.99x 加速，说明全局预测能够显著降低专家访问等待。

再次，预测收益依赖于缓存约束与预测质量的匹配。GPU expert cache 决定系统能够同时保留多少层-专家切片；当缓存过紧时，额外预取仍可能挤占当前工作集。真正有价值的是在有限显存下，把资源留给最可能在近未来被访问的专家。

最后，专家调度需要谨慎利用预测结果。实验中最有效的不是扩大预取集合，而是压缩候选集合：保留高置信度、近层、margin 足够大的专家，并通过保护当前访问专家和限制每层预取数量避免缓存被低价值专家污染。

上述结果也揭示了当前系统的两个边界。第一，视觉侧和专家侧优化分别带来了明确收益，但尚未在稳定的在线 serving 框架中形成完全闭环的端到端评估。由于完整链路会叠加 batching、KV cache、图像预处理、Python hook 和 expert cache 控制等因素，直接端到端数字更容易受环境波动影响。第二，当前预测器训练数据规模仍较小，主要覆盖固定模型和公开评测子集。若迁移到更长上下文、更复杂图文组合或不同 VL-MoE 架构，预测器可能需要重新采集 trace 并调整特征。

\section{本章小结}
本章对 Visual Encoder 优化和专家提前调度进行了实验评估。结果表明，SAT-ToMe 在保持任务效果稳定的同时，将 Visual Encoder 可见耗时降至 baseline 的 9.3\% 左右，并使整体 TTFT 获得约 1.63x 加速；专家侧全局预测器达到约 0.72 mean recall，在真实搬运场景下 predictor 与 oracle 都能显著降低同步等待，缓存容量则决定预测收益能否落地。
